# Статус проекта PlatformLove

Обновлено: 2026-09-15 (аудит авторизации по логину + PIN)

## Стек

- **Фронтенд**: React 19 + Vite 8 + Tailwind 4, React Router 7, Capacitor 8 (Android)
- **Бэкенд**: Node.js + Express 5, JWT, bcryptjs, multer, nodemailer
- **БД**: SQLite (`server/database.sqlite`), идемпотентная миграция `server/src/db/migrate.js`,
  демо-данные `server/scripts/seed.js`

## Авторизация

### Исправленный корневой баг

`src/api.js` кэшировал токен в конструкторе синглтона. После входа токен попадал в `localStorage`,
но экземпляр `api` продолжал слать запросы **без** `Authorization`, и все экраны после логина
работали как анонимные. Теперь токен читается актуально через геттеры `authToken` /
`authAdminToken` на каждый запрос.

Проверено headless-скриптом: запрос до логина идёт без заголовка, после логина заголовок
присутствует, `/api/auth/me` возвращает того же пользователя.

### Схема входа (актуальная)

СМС-входа в интерфейсе больше нет. Пользователь проходит один из путей:

| Сценарий | Поведение |
| --- | --- |
| Регистрация `/register` | имя + логин + **email (обязательно)** + пароль → токен → сразу `/set-pin` |
| Первый вход `/` шаг 1 | логин (или email) + пароль; PIN не задан → `/set-pin` |
| Обычный вход `/` шаг 2 | логин + пароль → экран «Введите PIN-код» → `/menu` (или `/profile`, если анкета пуста) |
| Установка PIN `/set-pin` | ровно 4 цифры, дважды; после сохранения → `/menu` или `/profile` |
| Забыли PIN или пароль `/forgot-password` | логин → код на email (6 цифр, 15 минут) → смена пароля и/или PIN |
| Выход | `api.logout()`; на `/set-pin` есть «Выйти и войти позже» |

`localStorage.pin_login` запоминает логин: при следующем открытии экран входа
сразу начинается с шага 2 (ввод PIN), пароль вводить не нужно.

### Обязательность PIN и защита маршрутов

`RequireAuth` (layout-роут в `src/App.jsx`) разворачивает на `/` все экраны, требующие токена:
`/profile`, `/questions`, `/menu`, `/swipe`, `/wall`, `/match`, `/likes`, `/fans`,
`/notifications`, `/messages`, `/feed`, `/friends`, `/user-profile`, `/chat/:id`,
`/settings`, `/subscription`, `/blacklist`.

Два уровня проверки PIN на клиенте:

- `RootGate` на `/`: онбординг → (есть токен ? (`hasPin === false` → `/set-pin`, иначе `/menu`) : форма входа);
- `RequireAuth` дополнительно разворачивает на `/set-pin` любой защищённый экран, если у
  сохранённого пользователя `hasPin === false`. До правки 15.09 проверка жила только на `/`,
  и не дошедший до PIN пользователь мог открыть `/menu` напрямую по URL.

**Важно:** это только клиентский барьер. Сервер PIN не требует — любой запрос с валидным
JWT проходит независимо от наличия PIN. Жёсткая серверная проверка сейчас заблокировала бы
существующие аккаунты без PIN (на проде их большинство), поэтому она не включена.

### Проверка флоу (смоук-тест)

`node server/scripts/smoke-auth-pin.mjs [base_url]` — 16 проверок реального HTTP-флоу
против запущенного бэкенда: отказ регистрации без email, `requiresPin`, вход по email
вместо логина, хеш PIN в БД (не открытый текст), неверный/верный PIN, `forgot-password`
→ код в `password_reset_codes` → смена только PIN, одноразовость кода, `/me`.
Тестовая учётка `smoke*` создаётся и удаляется самим скриптом; пароль генерируется
на ходу и в репозиторий не попадает. Логины/пароли боевой базы скрипт не трогает.

### SMS-эндпоинты (наследие, в интерфейсе не используются)

Экрана входа по СМС в приложении нет, но маршруты в `server/src/routes/auth.js` остались:

- `POST /api/auth/send-code` — 4-значный код, срок жизни 5 минут, лимит 5 попыток;
  в не-продакшене возвращает `debug_code` (проверено на проде: `NODE_ENV=production`,
  кода в ответе нет);
- `POST /api/auth/verify-code` — проверка с лимитом попыток, одноразовость,
  **создание аккаунта без email и пароля** при первом входе по номеру.

Второй пункт — лишний вход в обход схемы «email обязателен»: такой аккаунт нельзя
восстановить. Маршруты стоит удалить или закрыть фича-флагом; пока это мёртвый код.
Реальной отправки SMS нет: `SMSC_*` в env не подключены к провайдеру.

## Найдено и исправлено при аудите прода (15.09)

### Service worker ломал показ обновлений

Старый `public/sw.js` кэшировал `index.html` по принципу «сначала кэш» и содержал
захардкоженные имена бандлов прошлой сборки. После любого деплоя браузер отдавал
пользователю старый `index.html`, тот запрашивал уже несуществующие JS/CSS —
и приложение показывало пустой экран. Новое поведение:

- навигация и `index.html` — всегда сеть, кэш только как офлайн-запас;
- `/assets/*` — можно кэшировать (хэш содержимого в имени файла);
- `/api` и `/uploads` — не кэшируются никогда: это данные конкретных пользователей;
- `install` не падает из-за отсутствия одного файла, `activate` удаляет старые кэши
  и вызывает `clients.claim()`, чтобы новая версия вступила сразу.

Регистрация SW перенесена в `src/main.jsx` и работает только в production-сборке.
В разработке SW, наоборот, снимается, а кэши вычищаются — иначе правки «не применялись».

### Админка была доступна без входа

`/admin` открывался напрямую по URL: проверки сессии не было, а экраны при 401
дорисовывали демо-данные. Теперь `AdminLayout` сверяет токен с сервером через
`GET /api/admin/me` и при отказе редиректит на `/admin/login`. Локальный PIN
больше не заменяет серверную проверку: принимается только после подтверждения
email/пароля в этой сессии и хранится как SHA-256, а не открытым текстом.
Выход теперь действительно удаляет `admin_token`.

### Профиль жил только в браузере

Анкета, имя, город, фото и обложка сохранялись в `localStorage`, поэтому на другом
устройстве профиль был пустым, а в свайпах другим показывалась старая запись из базы.
Теперь сервер — источник истины, `localStorage` только кэш. Галерея хранит ссылки
`/uploads/...` вместо base64: двенадцать фото в base64 выбивали квоту `localStorage`,
и приложение ломалось. Заодно `uploadPhoto` читал устаревшее поле токена и уходил
без `Authorization`.

### Размер бандла

Админка вынесена в 16 ленивых чанков (`React.lazy` + `Suspense`): главный бандл
562 → 437 КБ, предупреждение Vite о чанке >500 КБ ушло.

## Известные ограничения

- **Email нельзя добавить или изменить после регистрации.** Поле есть только в форме
  `/register`, `PUT /api/users/:id` его не принимает. Из-за этого 22 боевых аккаунта
  (созданы до обязательной почты) восстановить доступ по почте не смогут — только
  через поддержку/админку. Нужна доработка: поле email в профиле с подтверждением кодом
  + разрешить его в `users.js`.
- Сервер не проверяет наличие PIN: барьер только на клиенте (см. «Обязательность PIN»).
- SMS-маршруты `send-code` / `verify-code` остались в API, хотя входа по СМС в интерфейсе
  нет; `verify-code` умеет создавать аккаунты без email и пароля.
- Реальной отправки SMS нет (`SMSC_*` в env не подключены к провайдеру). Отправка email
  на проде работает: SMTP-креденшелы в `server/.env` боевого сервера, в логах systemd
  есть доставленные письма (`✅ Email отправлен: …`). В не-продакшене без SMTP-ключей
  `sendEmail` работает в mock-режим и печатает письмо в консоль.
- Платежи — демо-режим: `POST /api/subscriptions` записывает подписку без внешнего эквайринга.
- Экран анкеты (`/profile`, `/questions`) сохраняет черновик локально; ответы уходят в
  `/api/filters/answers`, но базовые поля профиля на сервер не пишутся.
- Часть таблиц админки и соц-данных наполняется сидом для демо.
